# Wire format v1

Status: **Superseded by `payload-v2.md`**, but still accepted by the receiver for
backward compatibility. New clients send v2. Sections 3-5 and 7-8 remain
normative for both versions.

Binding contract. Both halves implement against this file.
Changing the meaning of an existing field requires a version bump, not a silent edit.

Part of the versioned wire contract; see `protocol/README.md`.

## 1. Endpoint

```
POST https://<home-assistant>/api/webhook/<webhook_id>
Content-Type: application/json
Authorization: Bearer <token>
```

Two independent values, both generated by the integration's config flow:

| Value | Role | Notes |
|---|---|---|
| `webhook_id` | addressing | appears in the URL, may reach proxy logs, **not** the credential |
| `token` | authentication | 256-bit random, compared with `hmac.compare_digest`, never logged |

TLS is required. The iOS app refuses `http://` unless the local-development override is
explicitly enabled in Settings.

## 2. Envelope

Every request body is a single JSON object.

```json
{
  "version": 1,
  "type": "sync",
  "sent_at": "2026-09-02T21:15:00Z",
  "device": {
    "name": "Pascals iPhone",
    "model": "iPhone17,1",
    "os_version": "26.5"
  },
  "samples": [],
  "daily_totals": [],
  "deletions": []
}
```

| Field | Type | Required | Meaning |
|---|---|---|---|
| `version` | int | yes | Wire format version. v1 receivers reject anything else. |
| `type` | string | yes | `"sync"` or `"ping"`. |
| `sent_at` | RFC 3339 UTC | yes | When the client built the payload. Diagnostic only; never used as a sample timestamp. |
| `device` | object | yes | Identifies the sending device. Contains no health data. |
| `samples` | array | no | Discrete samples (§3). Absent or `[]` is valid. |
| `daily_totals` | array | no | Cumulative daily totals (§4). Absent or `[]` is valid. |
| `deletions` | array of UUID strings | no | Samples removed from HealthKit (§5). |

`type: "ping"` carries no `samples`, `daily_totals` or `deletions`. It exists so **Test
Connection** can prove reachability, TLS and authentication without writing any data.
A receiver that sees `type: "ping"` must not modify state.

## 3. `samples` — discrete readings

Produced by `HKAnchoredObjectQuery`. One entry per HealthKit sample, original timestamps
preserved.

```json
{
  "metric": "heart_rate",
  "uuid": "3F2504E0-4F89-11D3-9A0C-0305E82C3301",
  "start": "2026-09-02T20:14:31Z",
  "end": "2026-09-02T20:14:31Z",
  "value": 62,
  "unit": "count/min",
  "source": "Apple Watch"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `metric` | string | yes | Metric key (§6). |
| `uuid` | UUID string | yes | HealthKit sample UUID. The idempotency key. |
| `start` | RFC 3339 | yes | Sample start, as recorded by HealthKit. |
| `end` | RFC 3339 | yes | Sample end. Equals `start` for instantaneous readings. |
| `value` | number | yes | Value in `unit`. |
| `unit` | string | yes | Canonical unit for the metric (§6). |
| `source` | string | no | Originating device/app name, e.g. `Apple Watch`. Free text. |

Server-side write is `INSERT … ON CONFLICT (uuid) DO NOTHING` — a replayed sample is a
no-op, never a duplicate.

## 4. `daily_totals` — cumulative metrics

Produced by `HKStatisticsCollectionQuery` with `.cumulativeSum` over daily buckets in the
device time zone. A cumulative metric is **never** sent as raw samples; summing raw
samples would double-count overlapping iPhone / Watch sources.

```json
{
  "metric": "steps",
  "date": "2026-09-02",
  "time_zone": "Europe/Berlin",
  "value": 8423,
  "unit": "count"
}
```

| Field | Type | Required | Notes |
|---|---|---|---|
| `metric` | string | yes | Metric key (§6). |
| `date` | `YYYY-MM-DD` | yes | Local calendar day in `time_zone`, **not** UTC. |
| `time_zone` | IANA identifier | yes | The zone the day was bucketed in. Part of the key. |
| `value` | number | yes | Total for that local day. |
| `unit` | string | yes | Canonical unit (§6). |

The idempotency key is `metric | date | time_zone`. The write is
`ON CONFLICT DO UPDATE` — **replacing** the value, never adding to it. Today's total is
expected to be re-sent many times as it grows, and late Watch syncs revise recent days.

## 5. `deletions`

A flat array of HealthKit sample UUIDs that no longer exist on the device:

```json
"deletions": ["3F2504E0-4F89-11D3-9A0C-0305E82C3301"]
```

`HKAnchoredObjectQuery` returns deleted objects alongside additions; observer queries
alone never do. Without this, a reading deleted in the Health app would live in Home
Assistant forever.

- Applied in the same transaction as that batch's additions.
- Idempotent: deleting an unknown UUID is a no-op, not an error.
- Deleting a discrete sample does **not** rewrite a daily total; the next statistics
  query for that day supersedes it anyway.

## 6. Metric registry — v1

Phase 1 implements exactly two metrics. The registry is the single place both sides agree
on identifier, unit and kind.

| `metric` | Kind | HealthKit type | Canonical unit | HA device_class | HA state_class |
|---|---|---|---|---|---|
| `heart_rate` | discrete | `HKQuantityTypeIdentifierHeartRate` | `count/min` | — | `measurement` |
| `steps` | cumulative | `HKQuantityTypeIdentifierStepCount` | `count` | — | `total_increasing` |

An unknown `metric` is rejected per item, not per batch (§8).

## 7. Response

The receiver always answers with JSON.

Accepted:

```json
{
  "ok": true,
  "version": 1,
  "accepted": { "samples": 12, "daily_totals": 1, "deletions": 0 },
  "rejected": [],
  "server_time": "2026-09-02T21:15:01Z"
}
```

`type: "ping"` answers with the same shape, all counts zero, plus `"pong": true`.

Rejected items are reported individually without failing the batch:

```json
{
  "ok": true,
  "version": 1,
  "accepted": { "samples": 11, "daily_totals": 1, "deletions": 0 },
  "rejected": [{ "index": 4, "collection": "samples", "reason": "unknown_metric" }],
  "server_time": "2026-09-02T21:15:01Z"
}
```

| HTTP | Condition |
|---|---|
| 200 | Body parsed. Individual items may still appear in `rejected`. |
| 400 | Body is not JSON, or `version` / `type` is missing or unsupported. |
| 401 | Missing or wrong bearer token. Body carries no detail. |
| 413 | Body exceeds the size limit. |

Reason codes in `rejected`: `unknown_metric`, `bad_timestamp`, `future_timestamp`,
`bad_value`, `bad_uuid`, `missing_field`, `wrong_kind`.

**A 401 must be actionable but silent.** The receiver never logs the received token or
the expected one.

## 8. Limits

| Limit | Value | Rationale |
|---|---|---|
| Max body size | 1 MiB | Rejects runaway payloads before parsing. |
| Max `samples` per batch | 2 000 | ~414 KB at 207 B/sample — 40% of the body limit, so the two limits cannot collide. |
| Max `daily_totals` per batch | 400 | |
| Max `deletions` per batch | 5 000 | |
| Timestamp ceiling | `now + 5 min` | Clock skew tolerated; far-future rejected. |
| Timestamp floor | `2000-01-01` | Guards against epoch-zero garbage. |

Exceeding a collection limit rejects the request with 400; the client is expected to
batch. Malformed **items** are rejected individually (§7) so one bad sample cannot fail a
whole batch.

A body over `MAX_BODY_BYTES` is refused with **413** before parsing, on `Content-Length`.

> **Limits must stay mutually consistent.** `samples` was originally capped at 5 000,
> which encodes to ~1 035 000 bytes against a 1 048 576-byte body limit — roughly 1% of
> headroom, erased by a slightly longer `source` string. The cap is now 2 000.
> Home Assistant itself accepts 16 MiB (`http.MAX_CLIENT_SIZE`); 1 MiB remains this
> project's own abuse guard, deliberately far below it.

### Batching (client obligation)

A first sync has no anchor, so HealthKit returns the **entire** history — far beyond any
of these limits. The client must therefore page the read and split each page into bounded
deliveries. The rules that make this safe:

- **Bounded read.** `HKAnchoredObjectQueryDescriptor.limit` pages the query at the source,
  so a multi-year history never has to be held in memory.
- **Anchor advances per page, only after every batch derived from that page is accepted.**
  A failure mid-history keeps the pages already accepted and resumes at the first page
  that did not land. Nothing is skipped.
- **Re-delivery is safe.** Every write is keyed on a stable identifier — sample `uuid`,
  or `metric | date | time_zone` — so a resend after a failure is a no-op rather than a
  duplicate or a double-count.
- **Daily totals travel with the first delivery of a sync only.** They are
  replacement-based, so repeating them on every batch of a long history is pure waste.

The wire format is unchanged by batching: a batch is an ordinary `sync` payload. The
receiver neither knows nor cares how many batches a sync was split into.

## 9. What v1 deliberately does not carry

- No request signature. Replay safety comes from idempotency, not cryptography.
- No sessions (sleep, workouts) — Phase 4.
- No per-metric enable flags — the client sends what it was asked for; Phase 3 adds
  toggles.
- No pagination or resume cursor. The `HKQueryAnchor` stays on the device and is never
  transmitted.
