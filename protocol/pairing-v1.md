# Pairing protocol v1

How Home Assistant hands its credentials to the app. **Versioned separately from
the health wire format** — this carries one URL and one token and changes when
setup does; the wire format carries measurements and changes when the data model
does. Tying them together would mean a pairing fix forced a wire version bump.

Home Assistant is the only producer and the app is the only consumer, so
`custom_components/apple_health_sync/pairing.py` in this repository is the single
authoritative implementation. The client half is tested against a fixture
generated by that encoder, not against a second specification written by hand.

## 1. The code

```
eigenpuls://pair#<url-safe base64 of compact JSON, unpadded>
```

Decoded:

```json
{"reach":"remote","token":"…","url":"https://hooks.nabu.casa/gAbCdEf","v":1}
```

| field | | |
|---|---|---|
| `v` | int | Pairing version. `1`. Not the wire version. |
| `url` | string | Exactly where to POST. Already complete — the app appends nothing. |
| `token` | string | Bearer token, 256 bits of entropy. |
| `reach` | `remote` \| `local` | Whether this connection works away from home. |

Keys are sorted and JSON is emitted with no spaces, so the same inputs always
produce the same string — which is what lets a committed fixture be meaningful.

There is deliberately **no** device identifier, account, installation id, or
anything resembling one. None is needed to POST to a URL with a token, and each
would need justifying later.

The webhook id is not a field either: it is already inside `url` for a local
target, and for a cloudhook it is not part of the URL at all. The app never needs
it.

## 2. Why a fragment

The secret rides after `#`. A fragment is not transmitted to a server on an
ordinary HTTP request, so a pairing code mistyped into a browser instead of
scanned does not hand the token to whoever runs that host.

That is a mitigation for one specific mistake. It is **not** what makes the code
safe, and neither is base64 — **base64 is encoding, not encryption**. Anyone
holding the code holds the token.

## 3. Security properties, stated exactly

| | |
|---|---|
| what protects the webhook | the 256-bit bearer token, which the receiver checks with `hmac.compare_digest` |
| what protects the token in transit to the app | nothing but the fact that the code is displayed on the person's own screen and scanned by their own phone |
| what a screenshot of the QR is | a credential. Full access to deliver into this webhook. |
| where the code must never appear | logs, diagnostics, exception messages, bug reports, analytics |
| is the code single-use? | **No.** It stays valid until the token is rotated. Claiming otherwise would need server-side state that does not exist, and a false claim is worse than an honest one. |
| how to invalidate one | *Reconfigure* rotates the token. The old code stops working immediately. |

`PairingPayload.__repr__` is overridden to print `<redacted>` instead of the
token, because a dataclass repr is how a secret reaches a log without anyone
deciding to put it there. No function in the module formats a token into an
exception.

## 4. Reach

`remote` and `local` exist so the app can be honest rather than optimistic. A
local URL genuinely does not work on mobile data, and a setup flow that implies
otherwise produces a person who believes the app is broken.

| Home Assistant has | url | reach |
|---|---|---|
| an active cloud subscription | the cloudhook | `remote` |
| a usable external URL | that URL + `/api/webhook/<id>` | `remote` |
| only an internal URL | that URL + `/api/webhook/<id>` | `local` |
| none of the above | *no code is produced* — the flow shows an error |

## 5. What may be encoded

HTTPS is accepted wherever it points: the certificate is the phone's to
validate, and iOS refuses a self-signed one on its own (measured: `-1202`).
Self-signed TLS is therefore not supported, and no amount of configuration here
changes that.

Cleartext HTTP is accepted only for targets that are unambiguously on a home
network:

| allowed | refused |
|---|---|
| RFC1918 IPv4 — `10/8`, `172.16/12`, `192.168/16` | any public address or name |
| IPv6 unique-local — `fc00::/7` | loopback: reachable by Home Assistant, never by the phone |
| `*.local` names | link-local (`169.254/16`, `fe80::/10`): means no DHCP, and it is the address family that contaminated the P3 routing measurement |
| | a bare hostname: this side cannot know what the phone would resolve it to |

iOS permits cleartext to private addresses without an ATS exception — measured on
a real device — but it will just as happily send cleartext to a public host. **iOS
is not the guard. This is.**

## 6. Errors

Reasons are stable strings, and never contain the payload.

| reason | means |
|---|---|
| `bad_scheme` | not an `eigenpuls://pair` URI |
| `missing_payload` | no fragment |
| `malformed_payload` | not base64, or not a JSON object |
| `missing_version` | no `v`, or not an integer |
| `unsupported_pairing_version` | a `v` this build does not implement — the app can say "this app is too old", which is actionable |
| `missing_url`, `missing_token` | absent or empty |
| `bad_reach` | not one of the two values |
| `unusable_url` | fails §5 |
| `no_usable_url` | Home Assistant has no address worth offering (flow-level, not in a code) |

## 7. Compatibility

A consumer that does not implement a version **must refuse the code**, not
guess. `unsupported_pairing_version` exists so it can say why.

Adding an optional field is a v2. There is no field-level tolerance in v1: the
decoder validates what it knows and rejects what it does not recognise, for the
same reason the health wire format closed its buckets — a silently ignored field
is a setting the person believes they configured.
